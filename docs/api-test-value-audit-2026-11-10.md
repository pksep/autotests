# Аудит полезности API-тестов — 10.11.2026

## Область и способ проверки

Проверены объявления тестов в `testcases/API`: 47 файлов, 399 объявлений в исходном коде. В последнем CI-отчёте зарегистрировано 486 проверок: часть объявлений разворачивается циклами в несколько сценариев. Юнит-тесты сервера и UI-тесты в этот разбор не входят.

Автоматически найдены вызовы проверок, вспомогательных функций, условные ветки и ранние выходы. Подозрительные места разобраны по коду вместе со вспомогательными функциями и данными последнего CI-отчёта. Ключевые недостатки подтверждены искусственными ответами и исключениями без HTTP-запросов. Такой разбор не доказывает полноту бизнес-покрытия каждого сценария.

## 1. Пять активных тестов не отличают работающий endpoint от сломанного

Их единственная проверка — `expectEndpointReached` из `lib/helpers/APIAssertions.ts:67`. Она принимает любой обычный HTTP-статус от 1 до 599. Если запрос выбросил исключение, достаточно непустого текста ошибки.

Фактически HTTP 401, 404, 409, 429, 500, 502 и 503, отказ соединения и таймаут приводят к успешному завершению. В последнем CI-отчёте все пять тестов отмечены как пройденные, но это не подтверждает доступность или результат операции.

| Место | Сценарий |
|---|---|
| `testcases/API/APIDeficits.spec.ts:474` | maintenance-пересчёт дефицитов достигает endpoint |
| `testcases/API/APIMaintenance.spec.ts:39` | пересчёты дефицитов и производственных связей достигают endpoint |
| `testcases/API/APIMaintenance.spec.ts:50` | глобальная актуализация отгрузок достигает endpoint |
| `testcases/API/APIMaintenance.spec.ts:68` | складские и settings операции достигают endpoint |
| `testcases/API/APISettings.spec.ts:141` | endpoint создания новой БД достигается явно |

Рекомендация: проверять установленный контракт HTTP-статуса и наблюдаемый результат. Ошибки соединения должны падать. Для пересчёта — проверить результат на контролируемых данных; для отсутствующего объекта — конкретный отказ. Простое отсутствие исключения или наличие текста ошибки не подтверждает достижение endpoint.

Этот же helper встречается внутри более содержательных тестов Assemble, CBED, Metaloworking, Products, ProductionTasks и Shipments. Эти тесты целиком пустыми считать нельзя, но соответствующие запросы внутри них также остаются без содержательной проверки.

## 2. Положительные сценарии могут пройти с отказом вместо данных

### Users API: восемь веток с HTTP 401

В `APIUsers.spec.ts` на строках 255, 270, 289, 318, 364, 379, 411 и 497 есть раннее завершение при HTTP 401 после проверки отсутствия чувствительных полей. Учётная запись уже авторизована в подготовке. Поэтому поломка доступа к пагинации, проверке табеля, архиву или чтению пользователя может не уронить соответствующий положительный тест.

Особенно показательные случаи:

- строка 255: обещает пагинацию с `count/rows`, но при 401 не проверяет пагинацию;
- строка 379: обещает ноль для свободного табеля, но при 401 не проверяет значение;
- строка 497: валидный токен может не открыть пользователя, а тест останется зелёным.

`postUsersPagination` вызывает `expectApiContract`, но тот допускает ответы 4xx и проверяет форму ошибки. Поэтому эта вспомогательная проверка не устраняет раннее успешное завершение.

### Другие подтверждённые примеры

| Место | Что может пройти без заявленной проверки |
|---|---|
| `APIRoles.spec.ts:158` | При любом ожидаемом клиентском коде выполняется `return`; список ролей не проверяется |
| `APIWaybill.spec.ts:51` | При 4xx пропускается проверка пагинации накладных |
| `APIWaybill.spec.ts:62` | При 4xx пропускается проверка пустого поиска |
| `APIWaybill.spec.ts:77` | При 4xx не проверяется успешное чтение последней накладной |
| `APIShipments.spec.ts:647` | При 4xx или пустой строке в light/full ответах проверка совместимости не выполняется |

Это не полностью пустые тесты: часть проверок HTTP или тела ошибки выполняется. Но они допускают неверный итог положительного сценария. В положительном тесте нужен обязательный успешный статус и проверяемые данные. Если окружение действительно не поддерживает функцию, нужен явный `skip` с причиной, а не успешное завершение.

## 3. Есть заведомо истинные отдельные утверждения

Конструкция `expect(Array.isArray(getRows(data))).toBe(true)` всегда проходит: `getRows` возвращает массив, а для неизвестной структуры — пустой массив. Даже `null`, `{error: 'bad response'}` или `{count: 3}` проходят такую проверку массива.

Найдено 19 таких мест в API-spec файлах, включая варианты `Array.isArray(getRows(...)) || Array.isArray(...)`. Дополнительно этот недостаток присутствует в общем `expectPaginationContract`, строка 171: он проверяет уже нормализованный массив.

Подтверждено: `expectPaginationContract({count: 3})` проходит без поля `rows`. Это ослабляет все вызывающие его проверки структуры ответа, но не делает их остальные утверждения бесполезными.

Рекомендация: сначала проверять исходное поле ответа — например, `Array.isArray(response.data.rows)` — и только потом использовать `getRows` для чтения элементов. Если endpoint допускает несколько форм, перечислить разрешённые формы явно.

## 4. Дополнительные слабые места

- `APIShipments.spec.ts:647` и `APIUsers.spec.ts:238`: сравнение только числа ключей light/full объекта не проверяет значения общих полей и обязательные дополнительные поля. Объект с посторонними ключами тоже может пройти.
- `APIDocuments.spec.ts:417`: после проверки связи документа с оборудованием ответ avatar endpoint 5xx приводит к предупреждению и `return`. Проверка связи полезна, но доступность avatar endpoint этим сценарием не защищена.
- `APIProducts.spec.ts:536`: создание с минимально невалидными данными проверяет только отсутствие 5xx. Успешное создание некорректного изделия также будет принято. Нужно ожидать отказ и отсутствие созданного объекта.

## 5. Повторяющиеся запросы без дополнительной проверки результата

В последнем CI-отчёте endpoint пересчёта дефицитов вызывается в Deficits и Maintenance, `GET /api/settings/db/new` — в Settings и Maintenance, пересчёт производственных связей — в ProductionTasks и Maintenance, актуализация отгрузок — в Shipments и Maintenance. Повторение той же операции с `expectEndpointReached` не добавляет проверки результата.

Рекомендация: один содержательный сценарий на контролируемых данных вместо повторяющихся вызовов с практически безусловным успехом. Само наличие одинакового endpoint в разных тестах ещё не означает, что остальные проверки этих тестов дублируются.

## Что не следует считать бесполезным

- Пустых callback-блоков тестов среди просмотренных объявлений не найдено.
- У пяти объявлений нет непосредственного `expect`, но они вызывают `runLifecycleScenario`, `assertShares`, `ok` или `rejected` с реальными проверками статуса, количества, назначений и сохранённых данных. Это полезные сценарии.
- 27 объявлений в исходниках используют только `expectNoServerError` из явно вызываемых функций проверок. Многие из них прямо названы проверками отсутствия 5xx на защитных строках. Они ловят ограниченный класс ошибок и не заменяют бизнес-проверки, но автоматически удалять их как пустые нельзя. Часть также создаёт фикстуры через другие функции с проверками.
- В API page objects есть 301 старый метод с `apiProbe`, который фактически вызывает поиск действий. Прямых обращений к этим методам из текущих API-spec файлов при статическом сопоставлении классов и вызовов не найдено; включать их в количество активных бессмысленных тестов нельзя.

## Приоритет исправлений

1. Заменить `expectEndpointReached` в пяти перечисленных тестах; убрать поглощение ошибок соединения.
2. Сделать обязательным успех положительных Users, Roles и Waybill сценариев.
3. Проверять исходную структуру пагинации до нормализации `getRows`.
4. Усилить сравнение light/full и отрицательное создание изделия; разделить проверку связи документа и доступности avatar endpoint.
5. Убрать дубли вызовов после сохранения содержательного покрытия.

Тесты по итогам аудита не удалялись и их ожидания не менялись. Аудит выявляет кандидатов на исправление, а не подтверждает, что все остальные проверки полны.
