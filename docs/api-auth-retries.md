# Авторизация в API-тестах

Каждый API-модуль регистрируется отдельной группой в `main.spec.ts`. Его `beforeAll` и `afterAll` действуют только на этот модуль. Ошибка подготовки Users API больше не останавливает весь `all_api_tests`. Последовательные сценарии внутри модулей сохраняют зависимость шагов.

`lib/helpers/APILogin.ts` повторяет вход после HTTP 429, соблюдая `Retry-After` в секундах или в формате HTTP-даты. Если заголовка нет, ожидание составляет 61 секунду: сервер ERP блокирует учётную запись на одну минуту. Всего допускается до пяти запросов и до 125 секунд ожидания. При превышении лимита проверка завершается ошибкой. Для ожидания увеличивается время текущего теста или хука подготовки. Ошибки соединения автоматически не повторяются.

Общий `getAuthToken` использует этот механизм и сохраняет ограниченные повторы HTTP 5xx. Обычные проверки входа повторяют только HTTP 429; итоговые ожидания статусов для правильных и неверных данных остаются прежними. Ошибки других эндпоинтов не обрабатываются как ограничение входа.

Успешный вход перед каждым сценарием в группе «Вход» сбрасывает счётчик неверных паролей. Отдельная проверка ограничителя отправляет три неверных пароля, проверяет статусы `401, 401, 429` и отказ с правильным паролем во время блокировки. В `finally` она дожидается окончания блокировки, проверяет успешный вход и завершает сессию.

Сессия берётся из cookie контекста запросов; содержимое cookie и пароли не выводятся в сообщения проверок.

Проверка изоляции самого раннера, без запросов в ERP:

```powershell
node scripts/check-api-runner-isolation.cjs
```

Она намеренно вызывает ошибку подготовки одного модуля и ошибку шага последовательного сценария, затем проверяет продолжение остальных модулей. Дополнительно проверяется восстановление после 429 внутри короткого `beforeAll`.

Для проверки на dev используйте обычный вход через `main.spec.ts`: `TEST_SUITE=auth_api`, затем `TEST_SUITE=all_api_tests`. Для полного набора не включайте `API_INDEPENDENT_TESTS`.
