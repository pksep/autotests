# Проценты страниц и модальных окон

Набор `percentages_api` проверяет данные производственных страниц, производственного пути, комплектации и готовности отгрузок.
Включён в `all_api_tests`, `api_functional_tests`, `api_contract_tests`,
`api_negative_tests` и последовательную группу `api_serial_heavy_tests`.

## Запуск

Из корня autotests с настроенными `API_TEST_USERNAME`, `API_TEST_PASSWORD`,
`API_TEST_TABEL`:

```powershell
$env:TEST_SUITE = 'percentages_api'
$env:API_BASE_URL = 'https://dev.pksep.ru/'
pnpm test
```

## Проверки

20 сценариев: по пять для детали, СБ и изделия, один для отгрузки,
четыре для невалидного необходимого количества.

| Источник | Метод и маршрут | Ожидание |
| --- | --- | --- |
| Страницы МО и сборки | `POST /api/metaloworking/pagination`, `POST /api/assemble/pagination` | Готовность по годным отметкам последней активной операции, а не среднее всех операций |
| Модалки производственного пути | `GET /api/metaloworking/:id`, `GET /api/assemble/:id` | Процент согласован со страницей и исходными отметками; повторное чтение сохраняет результат |
| Выбранное ПЗ | Те же GET с `productionTaskId` | `countCreated` согласован с `productionTaskMarks` выбранного ПЗ, исходные `marks` содержат общий набор; возврат A → B → A восстанавливает данные A |
| Контекст потребности | `GET /api/production-task/by-entity`, `GET /api/production-task/shipment/:type/:id` | Общая потребность равна сумме количеств ПЗ; количество выбранного ПЗ совпадает с его производственной позицией. GET shipment возвращает только общую потребность |
| Строки комплектации | `POST /api/specification/first-level-children` | Дети не исчезают из спецификации; процент каждой строки учитывает потребность родителя, остаток и готовые комплекты |
| Свободные остатки | `POST /api/detal/one`, `POST /api/cbed/one`, `GET /api/material/material/get/:id/true` | Свободный остаток равен `max(quantity − in_kit, 0)` |
| Покрытие по выбранному ПЗ | `GET /api/production-task/orders-summary/:type/:id`, `GET /api/production-task/by-id/:id` | Проверка учитывает складское покрытие позиции и комплекты, распределённые по операциям ПЗ |
| Шапка комплектации | `GET /api/production-task/percent/:type/:id` | Среднее точных долей покрытия детей; одинаковый материал в двух списках использует один остаток |
| Необходимое количество | Тот же GET с `requiredQuantity` | Значения 0, 0.5, 1, 350, 500 имеют приоритет над количеством ПЗ; дети без контекста ПЗ используют заданное количество |
| Отгрузка | `POST /api/shipments/pagination` | `lvl_complectation` совпадает с расчётом комплектации изделия на `kol` этой отгрузки |
| Валидация | GET процентов с `requiredQuantity=-1`, `NaN`, `Infinity`, `abc` | HTTP 400, структурированный ответ; последующий корректный запрос успешен |

Расчёты теста независимы от общих утилит приложения:

- Годное выполненное количество: сумма `max(kol − quantity_shipped, 0)`
  по отметкам без брака и отмены.
- Готовность производства: это количество на последней активной операции,
  делённое на `max(kolvo_shipments − kolvo_create, 0)`, с округлением до целого
  процента и ограничением 0–100. При нулевом знаменателе — 0.
- Для строки комплектации остаток складывается с количеством компонентов в готовых комплектах. В контексте ПЗ тест использует складское покрытие для этого задания и распределяет готовые комплекты по его операциям.
  Процент строки равен округлённой доле покрытой потребности и ограничен 100%. При нулевой потребности строки ожидается 0.
- Готовность шапки: среднее **неокруглённых** долей уникальных детей, округление
  только в конце. Повторяющиеся материалы группируются с суммой потребностей.
  Контракт шапки при нулевом необходимом количестве возвращает 100;
  пустая спецификация при положительном количестве возвращает 0.

## Данные и границы

Используются существующие активные записи dev; набор не создаёт отметки,
не меняет остатки и не запускает пересчёт. POST-запросы выше выполняют чтение.
ID не зафиксированы. Проверяются все строки первой страницы каждого типа,
до трёх информативных путей, до трёх отгрузок. Для переключения ПЗ поиск
ограничен двадцатью кандидатами первой страницы.

Нужны активные записи всех трёх типов с операциями, СБ и изделие с детьми
спецификации, а также сущности с двумя активными ПЗ. Для детали допускается
пустой `materialList`: заготовка и характеристики материала не входят в этот
контракт. Отсутствие необходимых данных приводит к явной ошибке предусловий,
а не к молчаливому пропуску. Набор рассчитан на стабильные данные в течение
проверки: параллельные изменения отметок или склада могут нарушить сравнение.

API-набор проверяет данные и арифметику, доступные интерфейсу. Отображение
процента в DOM, поведение индикатора загрузки и гонки ответов браузера требуют
отдельных UI-тестов. Общая сводка ПЗ с клиентским `totalPercent` в этот набор
не входит: в текущем интерфейсе это отдельное поле-заглушка.
