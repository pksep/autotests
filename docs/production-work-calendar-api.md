# API: изменение рабочего дня и рабочие субботы

Сценарии: `testcases/API/APIProductionWorkCalendar.spec.ts`.
Зарегистрированы в `production_tasks_api`, поэтому входят и в `all_api_tests`.

API записи: `POST /api/production-task/resource-workday`.
Поля: `entityType` (`ass` / `metall`), `resourceId`, `workDate` (`YYYY-MM-DD`), `minutes` (целое число 0–960).
Контракт сверен с dev-клиентом 06.11.2026: `ResourceWorkdaySchema`, `fetchSetResourceWorkday`.

Шесть тестов: по три для календаря станка (детали) и исполнителя (сборочные единицы).

1. Сохранение 4, 9, 16 часов и возврат к 8 часам; пересчёт срока операции длительностью 600 минут. Проверяются обед 13:00–13:30, неизменность соседнего дня и календаря другого ресурса.
2. Суббота 0 → 420 → 0 минут. При начале в пятницу в 08:00 операция заканчивается в понедельник в 10:00, после включения субботы — в субботу в 10:00, после отключения — снова в понедельник.
3. Отклонение отрицательных, превышающих 960, дробных, строковых и пустых минут, а также несуществующей и неверно записанной даты. После отклонения календарь не меняется.

Сохранение проверяется повторным чтением `POST /api/production-task/workload-by-entity`, окончание — отдельным `POST /api/production-task/tasks/operations`. После записи повторяются только запросы чтения, пока расчёт не завершится.

Тесты создают собственных сотрудников, станки, техпроцессы и ПЗ. Исходная продолжительность дней восстанавливается после каждого теста; временные объекты архивируются. Детали рассчитываются по станкам, сборочные единицы — по исполнителям. Известная ошибка отображения дат деталей в списке исполнителя остаётся в существующем тесте проверки дат.

Выборочный запуск через обычную конфигурацию проекта с настроенными переменными авторизации:

```powershell
$env:TEST_SUITE = 'production_tasks_api'
pnpm exec playwright test --grep 'Production Work Calendar API'
```
