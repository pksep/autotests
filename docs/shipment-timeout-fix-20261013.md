# Исправления автотестов №3 и №5 — 13.10.2026

Изменения ограничены проектом autotests по указанию пользователя.

## №3: операции созданного ПЗ

Сервер создаёт операции металлообработки через событие createProductionOperationPosEvent и фоновую очередь. Ответ о создании ПЗ может прийти раньше операций, поэтому немедленный GET возвращал production_operation_pos: [].

В APIProductionTasks.spec.ts добавлено ограниченное ожидание через существующий eventually: до 30 чтений с интервалом 1 секунда. Оно используется в жизненном цикле ПЗ и при создании фикстуры чтения. HTTP 200, отсутствие серверной ошибки и наличие операции остаются обязательными. Если очередь не завершит создание, тест падает с последним ответом сервера.

На dev после изменения прошли оба жизненных цикла: сборка и металлообработка (2 passed, 11.0s).

## №5: оформление отгрузки

Исходный сценарий после прихода изделия на склад оформлял отгрузку из статуса «Заказано».

Повторный запуск подтвердил HTTP 404 на POST /api/shipments/shcheck, заказ 5048, reqId=311ef26dbdc347aa408bcd8cb56d0749. Журнал API показал TimeoutError: unknown timed out в ShipmentsService.getShipmentWithShCheckByIds. PostgreSQL в 05:48:23.259 UTC зарегистрировал обновление заказа 5048 в «Просрочено» продолжительностью 5002.910 мс.

Сервер читает заказ с блокировкой в транзакции без date_shipments в выборке. AfterFind-хук Shipments.checkOverbye использует эту дату и обновляет статус без транзакции чтения. Обновление ждёт строку, которую удерживает вызывающая транзакция, а вызывающий код ждёт хук. Затем внутренний тайм-аут преобразуется в 404.

Автотест дополнен штатным подтверждением готовности после прихода изделия на склад: PUT /api/shipments/status/ready-to-ship/:id, { readyToShip: true }. Переиспользуется ShipmentsAPI.updateReadyToShipStatus, вызывающий тот же endpoint, что клиентский fetchUpdateReadyToShipStatus в таблице отгрузок. Сервер проверяет наличие складского остатка.

Тест проверяет успешный ответ, идентификатор заказа, статус «Готово к отгрузке» и его сохранение при повторном GET. После этого выполняются реальное оформление отгрузки, проверка складского списания, дефицитов и защита от повторного оформления. Ошибки API не принимаются за успех.

Сквозной сценарий с подтверждением готовности прошёл на dev (1 passed, 1.1m). Серверный дефект прямой отгрузки из других статусов остаётся неисправленным; серверные файлы не изменены.
